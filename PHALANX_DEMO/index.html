Scene 02 // The Urgent Dilemma

Why Giving AI Agents Payment Authority Fails

Unrestricted autonomous execution without deterministic guardrails exposes corporate treasuries to catastrophic financial loss.

⚠️ The Uncontrolled Agent Threat CRITICAL RISK
  • ✖
    Prompt Injection Vulnerability: Hidden adversarial text in supplier invoices can trick LLMs into rerouting payments to attacker accounts.
  • ✖
    Runaway Autonomous Loops: An agent caught in an automated retry or negotiation loop can drain thousands of dollars in minutes.
  • ✖
    Hallucinated Line Items: Probabilistic language models lack mathematical guarantees; numbers and currencies shift unpredictably.
  • ✖
    Zero Traceability: Standard credit cards and API keys leave no cryptographically verifiable explanation of why an action was taken.
🛡️ The PHALANX Governance Layer SECURE BOUNDARY
  • ✔
    LLM Barred from Authorization: The AI extracts messy text, but a pure mathematical engine makes the final spending decision.
  • ✔
    Cryptographic Ed25519 Mandates: Agents cannot exceed strictly signed budgets, allowed vendor lists, or velocity limits.
  • ✔
    Human Step-Up Safeguards: High-value transactions or unusual spending patterns automatically escalate to a supervisor.
  • ✔
    Immutable SHA-256 Ledger: Every event is hash-chained and locked against tampering with PostgreSQL database triggers.

Scene 04 // Cryptographic Integrity

Verifiable Identity, Mandates & Immutability

Four mathematically provable layers protecting every cent against spoofing, tampering, and repudiation.

01 Ed25519 Cryptographic Mandates 32-BYTE SEED

Before any agent operates, treasury signs an asymmetric Ed25519 keypair. The mandate establishes strict bounds: authorized vendor categories, maximum single transaction, daily limits, and valid time windows.

Key ID: key_a11878f59e66 // Alg: Ed25519 // Status: VALIDATED
02 RFC 8785 Canonical JSON Intent TAMPER PROOF

Prevents JSON serialization attacks. All fields are alphabetically sorted with zero arbitrary whitespace before hashing, ensuring bit-for-bit canonical reproduction across platforms.

sha256(canonical_jcs(payment_intent)) -> 64-hex digest
03 SHA-256 Merkle / Hash Chaining VERIFIABLE CHAIN

Every ledger event cryptographically binds to the previous event hash: current_hash = SHA256(prev_hash + sequence + event_data). Any historical record edit invalidates the entire chain.

Chain integrity verified across 100% of recorded transactions
04 PostgreSQL Database Write Triggers FAIL CLOSED

Database-level PL/pgSQL triggers explicitly reject any UPDATE or DELETE statements executed against ledger tables. Even an admin with direct SQL access cannot rewrite transaction history.

CREATE TRIGGER trg_deny_ledger_mutation BEFORE UPDATE OR DELETE

Scene 07 // Settlement & Traceability

Immutable Ledger & PayPal Sandbox Orders v2

Two-phase cryptographic authorization and capture with continuous database append-only verification.

💳 PayPal Sandbox Integration ORDERS V2

PHALANX connects to the live PayPal Sandbox Orders v2 API. Rather than executing raw charges, it executes a strict two-phase commit:

  • 1. Create & Authorize: Order generated with unique idempotency key.
  • 2. Policy Verification: Cryptographic mandate validation in 0.4ms.
  • 3. Capture: Released only upon final receipt verification and signature match.
