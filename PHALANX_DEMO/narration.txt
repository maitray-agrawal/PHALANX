=== SCENE 2: ARCHITECTURAL INTEGRITY (0:45 - 1:30) ===
To make autonomous payments safe, we have to change the architecture completely.
In PHALANX, the core design principle is absolute domain isolation.
Look at how a transaction moves through our system.
An autonomous agent receives an invoice and uses an LLM, like Google Gemini 2.5 Flash, to interpret messy unstructured text and extract key fields.
However, notice the strict security boundary: the language model is strictly barred from the authorization boundary. The LLM cannot authorize, sign, or execute a single payment.
Instead, the extracted transaction parameters are converted into an immutable payment request and passed into the PHALANX Domain Core.
This domain core is completely pure. It performs zero network I/O, makes zero clock lookups, and runs zero probabilistic code. It evaluates the transaction against strict mathematical policies in under half a millisecond.
The policy engine produces exactly one of three deterministic outcomes:
First, ALLOW: the payment is completely within pre-authorized mandate limits and is immediately scheduled for settlement.
Second, STEP_UP: the transaction exceeds routine thresholds, triggering mandatory human supervisor approval.
And third, DENY: the request violates spending bounds, targets an unapproved vendor, or exhibits signs of tampering, and is rejected immediately.
Every single decision leaves an accountable cryptographic record.

=== SCENE 3: CRYPTOGRAPHIC MANDATES (1:30 - 2:15) ===
How does PHALANX know what an agent is actually authorized to do?
Through Ed25519-signed agent mandates.
Before any financial agent can initiate a transaction, the organization issues a cryptographic mandate signed with an Ed25519 private key.
This mandate defines strict boundaries: the agent's unique ID, authorized vendor categories, maximum single-transaction amounts, daily and lifetime velocity caps, and allowed payment rails.
When an agent submits a payment request, PHALANX computes an RFC 8785 canonical JSON digest of the intent. This ensures that field order, whitespace, and formatting cannot be manipulated to alter the signature.
If even a single character, decimal place, or vendor account number is tampered with in transit, the signature check fails immediately, and the transaction is aborted.
No agent can spend outside its signed mandate. Period.

=== SCENE 6: IMMUTABLE AUDIT LEDGER & PAYPAL SETTLEMENT (4:30 - 5:15) ===
Every single action taken inside PHALANX is written to an immutable, append-only audit ledger.
Each ledger event is cryptographically linked to the previous event using a SHA-256 hash chain, exactly like a high-performance private blockchain.
At the database layer, PostgreSQL triggers physically block any UPDATE or DELETE operations on ledger rows. Even a database administrator with raw SQL access cannot alter historical audit records without raising a cryptographic alert.
Anyone can click 'Verify Ledger Integrity' at any time to re-compute the hash chain across all events and prove that the records have never been tampered with.
When transactions are approved, PHALANX executes real settlement through PayPal Sandbox using PayPal Orders v2.
We enforce a two-phase commit: the funds are first authorized against the merchant order, and only captured once the goods receipt and policy checks are finalized.
Every PayPal capture ID, timestamp, and signature is immutably anchored to the ledger.
